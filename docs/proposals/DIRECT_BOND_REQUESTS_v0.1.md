## Existing implementation and safe reuse

- `src/living-atom/interaction/AtomContextPanel.tsx` owns the selected-Atom context and VIEW THEIR NETWORK control. `atom-context.ts` uses deterministic graph distances from the original viewer. `LivingAtom.tsx` routes individual canvas/selector inspection into this panel. Recentring changes perspective, not ownership. Aggregated map regions are not individual request recipients.
- `src/components/auth/NetworkPage.tsx` distinguishes owner and public views. Public exploration can load another component; visible/selectable alone is not request authorization. Offer requests only in the verified ACTIVE owner's experience and revalidate against that owner's database network.
- `private.reachable(uuid)` in `202610180001_active_network_home_region.sql` traverses confirmed Bonds through ACTIVE endpoints only. Its 5,000-member limit fails closed. Reuse it at creation and acceptance; do not introduce a second traversal or trust client graph data.
- `ownerContext()` validates the Supabase user and obtains `my_atom()`. Existing `requireOwner()` and `private.owner_atom()` also permit DORMANT. Do not change them globally. New operations must use the existing verified live-session ownership resolution (`private.account_owner()`) plus an explicit ACTIVE check.
- `SupabaseBondService.confirm(token)` calls `accept_bond_invitation(text)`. That function is wrapped by `private.lifecycle_lock()` and accepts a bearer invitation, not a named-recipient request. Its underlying function inserts the canonical ordered pair into `public.bonds`, whose unique pair constraint prevents duplicates. It consumes the invitation and its encrypted secret in the same transaction.
- General invitations permit one outstanding invitation per creator and use the universal 24-hour deadline. Reusing such a record for a seven-day request would alter external invitations, impose the wrong limits and expose an inappropriate transferable credential. There is no reusable generic recipient-bound confirmation RPC.
- `BondConfirmation.tsx` supplies existing consent language, pending/error handling and confirmed-network presentation, but directly invokes token/registration confirmation. Reuse presentation through an injected action or a small shared presentation component; preserve its current callers and registration receipt handling unchanged. Do not pretend a request UUID is an invitation token.
- `OwnerExperience.tsx` already owns network refresh, Bond presentation and installation invitation composition. It has no private recipient inbox. Network Signal is an administrator broadcast, and InstallOffer is installation-specific; neither is safe storage or transport for personal requests.
- `public.bonds.origin_invite_id` is nullable. Repository references found only its schema and external acceptance insert. A direct request can reference its resulting Bond privately without fabricating an external invitation or changing the Bond table. Test existing graph/growth calculations before relying on this property.

Conclusion: existing authentication, graph traversal, lifecycle lock, canonical Bond constraints and consent presentation are reusable. The existing token acceptance service cannot safely implement this feature unchanged. A separate, narrowly authorized request-acceptance RPC is necessary; the external acceptance function need not be edited or refactored.

## Approved Task #21.1 policy alignment

| Policy            | Proposed rule                                                                                                                                                                                                                                                                                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Consent           | Sender explicitly requests; only the named recipient may explicitly ACCEPT BOND. Reverse requests never auto-accept.                                                                                                                                                                                                       |
| Lifetime          | Exactly 168 hours from database creation; at the deadline a request cannot be accepted, regardless of cleanup. No extension on retry.                                                                                                                                                                                      |
| Uniqueness        | One pending request per ordered sender/recipient pair. Retry returns that same request. Opposite-direction requests may coexist; one acceptance closes the other as superseded without a second Bond.                                                                                                                      |
| Decline retry     | Thirty days before that sender may request that recipient again. Cancellation or reactivation cannot clear this deadline.                                                                                                                                                                                                  |
| Volume            | Five newly created requests per sender per rolling 24 hours; at most ten pending outgoing requests; no additional incoming cap. Retries do not spend another allowance. Add bounded per-owner/ingress operation throttles; no administrator exemption.                                                                     |
| NOT NOW           | Mark the notice seen server-side; retain the pending request in BOND REQUESTS on MY ATOM. No Bond or automatic decline.                                                                                                                                                                                                    |
| Notification      | One modal per visit, showing at most one new request; server-side atomic notice claim prevents repeated pop-ups across reloads/tabs/devices. Claim-before-display can lose a popup after a crash, but never loses the pending list entry. Defer InstallOffer until request dialog closes. No emails or push notifications. |
| Cancellation      | Sender may cancel a pending request. Cancellation, decline and acceptance serialize; the first valid terminal transition wins.                                                                                                                                                                                             |
| Opt-out           | Receiving is initially allowed. A private toggle in Settings disables future requests and cancels current incoming requests. Re-enabling does not restore them. Return generic unavailability to senders, not the private preference.                                                                                      |
| Account lifecycle | Becoming non-ACTIVE invalidates pending requests involving that endpoint; reactivation never resurrects them. A changed bridge/path is revalidated on use and acceptance. No alteration to retained confirmed Bonds.                                                                                                       |
| Retention         | Closed request metadata retained for at most 30 days after closure; no free-text messages. Preserve decline/retry controls only until their deadline. Account deletion immediately erases associated request, notice and preference records; retain existing anonymized confirmed Bond records under existing policy.      |

These policies are approved for local implementation; frozen v0.10 is unchanged. A bounded atomic notice claim gives at-most-once automatic presentation, not a guarantee that a human saw a notification.

## Candidate migration design

Provisional identifier: `202610250001_direct_bond_requests` (recheck migration synchronization before any future publication).

1. Add private request, recipient-preference and compact rate/pair-cooldown records. Request fields: opaque UUID, sender/recipient Atom foreign keys, database creation/deadline, state, notice-claimed timestamp, closed timestamp, resulting Bond ID and purge deadline. No emails, auth IDs, tokens or message text in UI serialization. Use a partial unique index for pending ordered pairs and indexes for bounded recipient reads and expiry/purge scans. Retire expired pending rows transactionally before a new request; never use volatile time in an index predicate.
2. Enable RLS and revoke all client table access. Expose only narrow security-definer RPCs with empty search_path, explicit authenticated grants and per-operation ownership checks. Revoke default PUBLIC execution and all private helper execution. No broad credential, new token issuer or new authentication flow.
3. RPC operations: eligibility/pending summary, create, list, atomically claim one unseen notice, dismiss, decline, cancel, accept and update the caller's receiving preference. Never accept a caller-supplied owner or administrator identity. An opaque UUID identifies a request but grants no authority. Return only the minimum endpoint public number, state/deadline and authorized actions.
4. Each mutation first acquires the existing lifecycle lock, then resolves a verified live owner and requires ACTIVE status. Creation and acceptance require both ACTIVE endpoints, recipient opt-in, no direct Bond and target membership in `private.reachable(sender)`. Public-view roots do not change this check. If reachability exceeds its existing bound, return unavailable without broadening access.
5. Acceptance locks the request and checks its recipient, state and deadline using database time after locks are acquired. Revalidate endpoint eligibility and current network path. Insert one canonical CONFIRMED Bond with confirmed_at; link the request to it and close reciprocal pending requests atomically. The pair uniqueness constraint remains the final defense against external-invitation acceptance races. Do not resurrect a non-confirmed historical pair or overwrite existing Bond metadata. An already-direct pair resolves as already bonded/superseded, not another success animation. A retry of this accepted request by its recipient returns its existing result only after current owner authorization.
6. Use an additive account-status trigger to invalidate pending request state on deactivation/dormancy and physically erase applicable private data on deletion, without replacing existing lifecycle functions. Do not resurrect records on activation. Test trigger ordering and rollback under the existing lifecycle lock. A path broken by a third-party bridge change is denied at read/acceptance; do not claim all such paths are proactively recomputed.
7. Add bounded, idempotent expiry/purge cleanup with counts and last-success/failure diagnostics. Cleanup is not an authorization dependency. Prepare reuse of existing pg_cron infrastructure as a separate job; do not alter Doodle, Puzzle, EVOLVE or Weekly Growth jobs. No hosted job in this local task. Tests must establish physical deletion and deadline precedence.

Tradeoff: a separate acceptance RPC adds a small second authorized entry point to the existing Bond table. It avoids changing the proven external-token flow, but requires independent security/concurrency proof and maintenance of the same constraints. Extracting a shared insertion primitive would touch external confirmation and is not recommended in this scope.

## UI integration plan

Pass an optional request-action slot/callback from OwnerExperience through LivingAtom into AtomContextPanel. Keep service calls out of the visualization subsystem. Show REQUEST DIRECT BOND only for an eligible indirect individual; pending becomes REQUEST PENDING with cancellation available in the request list. Hide actions in synthetic/public/inactive/self/direct/unreachable contexts. A server denial after graph changes refreshes context and shows neutral recovery text.

Add a compact BOND REQUESTS entry in MY ATOM, not production primary navigation. Its list can reopen pending incoming requests and cancel outgoing ones; no chat, feed, ranking or contact information. Existing confirmation styling, keyboard focus management, error/live-status patterns and network refresh are reused. Only a successful authoritative acceptance displays success and refreshes the confirmed network. Dismissal returns focus normally and does not invoke login or invitation callbacks.
